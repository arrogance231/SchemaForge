# Training Report — loop-iter0-20260809T073238Z

## What this document is

A provenance record for one specific training run of the SchemaForge V2 pipeline, written for
someone who will read the eventual GitHub repository and needs to understand **how this specific
checkpoint was produced**, without necessarily reading the training code. It complements — does
not replace — the Hugging-Face-facing model card already written for the checkpoint this pipeline
produces (`models/distilled_minicpm5_1b_v2_amd/README.md` on the training server) and the
iteration-by-iteration research log at `logs/V2_TRAINING_FAILURES.md`, which remains the
authoritative record of results and negative findings.

**Everything in this document is either directly measured from the running process/git
history/on-disk config at audit time, or explicitly marked `unknown — not recorded` with a note
on where it could be recovered from. Nothing here is guessed or reconstructed from what a
"normal" run would look like.**

## What was trained

The SchemaForge V2 sequence-level knowledge distillation pipeline: an ~1.04B-parameter student
(`openbmb/MiniCPM5-1B`) is trained by cross-entropy on JSON-extraction outputs generated offline
by a `google/gemma-4-31B` teacher, filtered through a 4-step validation gate before admission.
This is the loop-orchestrated version of the pipeline (`src/09_loop.py`), chaining hard-example
generation, teacher query + gate, retraining, hybrid-pipeline benchmarking, and failure analysis
as one deliberate iteration.

## Why distillation, and the teacher → student relationship

Per `docs/PROJECT_CHARTER.md`: the goal is a small, fast, self-hostable extraction model that
approaches a much larger teacher's structured-extraction quality at a fraction of the inference
cost. The teacher (`google/gemma-4-31B`) is queried offline, never at student inference time; the
student (`openbmb/MiniCPM5-1B`, ~1B params) is trained purely on the teacher's *validated* text
outputs via cross-entropy — there is no logit-level distillation. An earlier version of this
project (V1) used cross-tokenizer logit KL divergence between teacher and student; that was found
invalid (the two models don't share a tokenizer, so aligning logit distributions token-for-token
doesn't mean what it appears to) and was dropped, documented in `docs/PROJECT_CHARTER.md` §7.1.
This run does not revisit that decision.

## Training methodology

- **Objective**: `torch.nn.CrossEntropyLoss(ignore_index=-100)`, computed only over the teacher's
  completion tokens (the prompt is masked to `-100`). No teacher forward pass, no KL term, no
  alpha/beta loss weighting — a single CE loss.
- **Optimizer**: AdamW, learning rate `2e-5`, weight decay `0.01`, gradient clipping at max norm
  `1.0`.
- **Schedule**: cosine learning-rate schedule with a 2-step warmup.
- **Epochs**: 3, over whatever count of gate-admitted examples the teacher stage produces (not
  fixed in advance — depends on the §4.2 gate's rejection rate for this corpus).
- **Batch size**: 2 (no gradient accumulation, so effective batch size is also 2).
- **Sequence length**: up to 1024 tokens (prompt + completion), truncated; an example whose prompt
  alone exceeds 1024 tokens raises an error rather than silently training on an all-masked label
  (this has not triggered in any run so far).
- **Precision**: resolved at runtime — bf16 on this hardware (MI300X supports bf16), falling back
  to fp16 only if unsupported. Not yet confirmed from this run's own log at time of writing (the
  retrain stage had not started when this report was drafted).
- **No PEFT/LoRA/quantization** — full-parameter fine-tuning.
- **No gradient checkpointing.**
- **Random seed for training itself is NOT set** (`torch.manual_seed()` is never called in
  `src/02_train_distill.py`) — this is a genuine reproducibility gap in the current script, not an
  omission of this report. The data-generation seed (`42`) IS fixed and produces a byte-identical
  corpus every time (verified — see Dataset section), but the training shuffle/init order is not
  reproducible as currently written.

## Dataset construction

Generated by this repo's own deterministic hard-example generator
(`schemaforge/hardexamples/generate.py`), not sourced from an external published dataset:

```
python3 -m schemaforge.hardexamples.generate --split train --n 30 \
    --severities 0.0,0.3,0.6,0.9 --seed 42 --out data/hard_examples_train.jsonl
```

- 1080 records across the 9 training schemas (the 3 held-out schemas — `insurance_claim`,
  `conversation`, `kg_triple` — are excluded by construction via `--split train`, never seen in
  training).
- SHA256 of the generated corpus: `94afb6bb4befb11679cc5390d5cd89ce6d1f5580d0851b84cf007194d97f72de`
  — confirmed byte-identical to the corpus used in the prior (iteration-5) run, verifying the
  generator's determinism claim.
- Every corruption operator's output is filtered through the §4.2 validation gate
  (`schemaforge/validation/gate.py`) before the teacher's label is admitted to training: JSON
  parse, Pydantic schema validation, source-support/ontology-derivation check, no-over-assertion
  check. Rejected examples are logged with per-step reasons (`data/teacher_dataset_rejections.json`),
  not silently dropped. The admitted count and rejection rate for THIS run were not yet available
  at the time this report was drafted (the teacher-generation stage was still in progress) — the
  prior run with the identical 1080-record corpus admitted 636/1080 (58.9%); this run's actual
  admitted count will be recorded once available and may differ slightly since teacher sampling is
  not perfectly deterministic across runs.
- No held-out validation/test split of the training corpus — the model trains on 100% of
  gate-admitted examples. Evaluation is against a wholly separate 72-record corpus
  (`data/eval_holdout.jsonl`), spanning all 12 schemas including the 3 held-out ones, generated
  independently rather than split from the training data.

## Known deviations / caveats already identified

1. **Training seed is not fixed.** `src/02_train_distill.py` never calls `torch.manual_seed()`;
   only the *data-generation* seed (`42`) is fixed and verified deterministic. This run's exact
   shuffle order and weight-init RNG state are not reproducible as the script is currently
   written. This is a pre-existing property of the script, not something introduced for this run.
2. **Checkpoint overwrite — confirmed, happened.** `src/02_train_distill.py` always writes to
   `./models/distilled_minicpm5_1b_v2_amd`, the same path as the prior (iteration-5) checkpoint.
   No `_iterN` backup was made before this run started (prior manual iterations renamed the
   previous checkpoint first; `src/09_loop.py` does not automate that step). **The iteration-5
   checkpoint's weights are now gone**, overwritten by this run's save — its evaluation numbers
   remain preserved in `logs/V2_TRAINING_FAILURES.md` and the eval JSON reports, only the weights
   themselves are unrecoverable. Fix for next time: have `src/09_loop.py` rename the existing
   checkpoint dir before retraining, the way the manual iterations did.
3. **Per-epoch loss and step count not recoverable.** `src/02_train_distill.py` prints per-step
   and per-epoch loss to stdout, but `src/09_loop.py`'s `_run()` helper calls
   `subprocess.run(capture_output=True)` and never prints or persists that captured stdout for the
   retrain step (it's only used to regex-parse the corpus-generation and teacher-gate stages'
   output) — so this run's full training log was captured by the OS pipe and discarded when the
   subprocess finished. Fix for next time: have each stage's subprocess redirect to its own log
   file (`> logs/<stage>_<run_id>.log`), the way every manually-launched run in this project's
   history did.
4. **Attention implementation unspecified.** No `attn_implementation=` argument is passed to
   `from_pretrained`; whatever Transformers' default resolves to for this architecture/dtype on
   ROCm is what ran. Not independently confirmed.
5. **No token-throughput instrumentation.** Neither `01_generate_teacher.py` nor
   `02_train_distill.py` logs tokens/sec or samples/sec; deliberately not added mid-run to avoid
   touching the active training process.

- **Training seed is not fixed** (deviation #1) — this run cannot be exactly reproduced even with

  proven, only plausible.
- **Per-epoch loss/step-count is lost for this specific run** (deviation #3) — the training
  dynamics (did loss converge smoothly, was there a spike, etc.) cannot be inspected after the
  fact for this run, only for the manually-launched prior iterations which redirected stdout to a
  file.
- **Attention implementation** was not independently confirmed (deviation #4).
