# V2 Training Failure Log

Per SCHEMAFORGE_V2_RESEARCH_DIRECTION.md §8: negative results and failures are recorded, not overwritten.

## Iteration 1 — 2026-08-08 — Teacher generation, HF-generate fallback

**Failure:** 0/15 teacher outputs parsed as valid JSON (`json.loads` failed on every record,
`Extra data` errors at ~line 17).

**Root cause:** `extract_json_str()` in `src/01_generate_teacher.py` only stripped markdown
code fences (` ```json ... ``` `). It performed no balanced-brace extraction. Under the
HF `generate` fallback (used because no ROCm vLLM build is installed on the AMD MI300X
server), the teacher model (`google/gemma-4-31B`) was not stopped at the natural end of the
first JSON object — with `max_new_tokens=512` it continued generating full new
"document + JSON" pairs after the target object closed, echoing the few-shot pattern
implied by the prompt style. The saved `teacher_json` field therefore contained the correct
JSON object followed by trailing hallucinated text (the model continuing to "complete" the
document set).

**This is the same defect class as PROJECT_CHARTER.md §7.4** (brace-matching JSON
extraction), but the opposite failure mode: §7.4 as originally written under-extracts
(truncates at the *first* `}`, corrupting nested objects); this occurrence *over-extracts*
(no stopping condition at all, so trailing hallucinated content leaks into the label).
Both are symptoms of "cut at first/last brace" not being a substitute for a real balanced
matcher.

**Fix:** replaced `extract_json_str()` with a balanced-brace scanner that returns the first
complete `{...}` object (tracking nesting depth, respecting string literals so braces inside
JSON string values don't miscount), instead of naive fence/split logic.

**Rejection rate this bounds:** 15/15 teacher records in this batch would have been rejected
by the §4.2 teacher-validation gate (JSON parse is gate step 1) had that gate existed at the
time this run happened before the fix — i.e. 100% label noise from this specific bug,
independent of model quality. Re-generated after the fix; see next entry.

## Iteration 6 — 2026-08-09 — Confidence calibration (§5): raw signal badly overconfident

**What ran.** New `schemaforge/calibration/` module (pure-math: reliability bins, ECE,
risk-coverage curve, coverage-at-risk, grid-search temperature scaling — 19 tests, all CPU-only)
plus `src/06_confidence_eval.py`, a GPU driver that runs the iteration-5 checkpoint
(`models/distilled_minicpm5_1b_v2_amd`, 636-example training run) over `data/eval_holdout.jsonl`
(72 records) with `output_scores=True`, derives a raw per-record confidence as the exp of the
mean token log-probability of the generated sequence, labels each record `correct` when its
field F1 >= 0.5, splits the 72 records in half (even/odd index) to fit temperature scaling on one
half and evaluate on the other, and reports risk-coverage/coverage-at-risk operating points.

**Result — the raw confidence signal is badly overconfident.** Raw confidences: min 0.737, mean
0.978, max 1.000 across all 72 records, while only 34/72 (47.2%) are actually `correct` under the
F1>=0.5 threshold — the model is emitting near-certain token probabilities on wrong extractions
about as often as on right ones. Calibration numbers:

| | value |
|---|---|
| raw ECE (fit half) | 0.4245 |
| raw ECE (holdout half) | 0.5871 |
| fitted temperature | **5.0000 (grid ceiling)** |
| calibrated ECE (holdout half) | 0.3608 |
| coverage @ risk<=0.10 | 0.3194 |
| coverage @ risk<=0.20 | 0.4306 |
| coverage @ risk<=0.30 | 0.4861 |

**This is a negative/partial result, reported per §8.** Temperature scaling improved holdout ECE
(0.5871 → 0.3608) but the fitted temperature landed exactly on the grid search's upper bound
(`hi=5.0` in `fit_temperature`'s default), meaning the true ECE-minimizing temperature is likely
higher than 5.0 and the search under-corrected — this is a real overconfidence the single-scalar
temperature-scaling approach struggles to fully absorb, not a calibration-fitting bug. Two
follow-ups, neither done yet: (1) widen the `fit_temperature` grid (`hi` well past 5.0) and
re-check whether ECE keeps improving or plateaus; (2) per research direction §5's own preference
ordering, mean token log-probability is listed as the fallback signal — self-consistency
(agreement across k sampled generations) or a trained calibration head are named as stronger
alternatives, and this result is exactly the kind of evidence that would justify the extra cost
of self-consistency sampling. The 34/72 correctness rate at F1>=0.5 also reflects that this eval
set includes the 3 held-out schemas the model was never trained on (same caveat as iteration 4).
Full report with per-record confidence/correctness: `logs/confidence_distilled_iter5.json`.

## Iteration 8 — 2026-08-09 — Failure analysis (§7): bug found + fixed, then real results

**Migration note.** This iteration ran on a new AMD server (`amd-training-2`, amd-training-2,
same MI300X GPU, ROCm 7.0.2, "rocm-7-14-software" template) — the original AMD box
(`amd-training`, amd-training) is still up and holds all prior checkpoints/data untouched. The
iteration-5 checkpoint was copied server-to-server and sha256-verified identical before use. Two
agents now operate against this new server concurrently; a `ufw` port-22 rate-limit (`LIMIT IN`,
~6 conn/30s) that was causing intermittent SSH refusals under concurrent use was found and
changed to a plain `ALLOW` — `fail2ban` had nothing banned, so it was not a factor.

**What ran.** New `schemaforge/failure_analysis/` module (`classify_record`/`build_report`,
implementing the 8 §7 categories + an honest `unclassified_mismatch` catch-all, 11 tests) plus
`src/07_failure_eval.py`, a GPU driver that generates over `data/eval_holdout.jsonl` (72 records)
with the iteration-5 checkpoint, evaluates each record, classifies every discrepancy, and
aggregates by category/schema/operator with worst-N examples.

**Bug found and fixed before trusting the numbers.** First run: `unclassified_mismatch` (236)
was the single LARGEST category, ahead of `missing_field` (219) — suspicious, since the whole
point of the catch-all is to be a small residual. Inspecting the worst examples showed every one
had `predicted=None` against a real reference value. Root cause: `evaluate_record` (in
`schemaforge/evaluation/metrics.py`, unmodified) uses `pred_flat.get(path)` to detect missing
fields, which cannot distinguish "key truly absent" from "key present with an explicit JSON
`null`" — both correctly land in `result.missing`. But an explicit-null key IS present in
`pred_flat`, so it ALSO lands in `result.errors` (present in both, values unequal), and
`classify_record` was emitting a second `FailureInstance` for it — always `unclassified_mismatch`,
since `None` isn't a string or `_is_scalar`. Fixed by skipping `errors`-dict entries where
`pred_value is None` in `classify_record` (one `continue`, with a comment on why, plus a
regression test asserting exactly one `FailureInstance` per such field). This is a bug in the new
failure-analysis module, not in `evaluate_record`/the core metrics (those aggregate counts —
n_correct/n_missing/n_hallucinated — were never double-counted; only this module's
per-instance classification was affected), so no prior iteration's precision/recall/F1/ECE
numbers need revisiting.

**Corrected result (72-record eval set, iteration-5 checkpoint, 636-example training run):**

| category | count | share of 354 |
|---|---|---|
| missing_field | 219 | 61.9% |
| unclassified_mismatch | 75 | 21.2% |
| hallucinated_field | 29 | 8.2% |
| incorrect_nesting | 14 | 4.0% |
| ambiguous_input | 7 | 2.0% |
| wrong_entity_boundary | 7 | 2.0% |
| schema_violation | 3 | 0.8% |
| incorrect_normalization | 0 | 0.0% |
| wrong_inferred_value | 0 | 0.0% |

**The dominant failure mode by a wide margin is omission (missing_field, 62%), not
commission** (hallucination is 8%, schema violation under 1%). Per-schema breakdown shows
`missing_field` skews toward the 3 held-out schemas the model was never trained on
(`conversation` 28, `insurance_claim` 27 — among the highest counts despite similar record
counts to trained schemas), consistent with a real generalization gap rather than a uniform
extraction weakness. The residual `unclassified_mismatch` (75, still the second-largest bucket)
is now populated by genuine near-misses the current precedence order doesn't have a bucket for —
e.g. OCR-corrupted surface forms the model gets almost-but-not-quite right (`"Northwijd Systems"`
predicted vs `"Northwind Systems"` reference — not a clean substring match so it misses
`wrong_entity_boundary`), and outright garbled/confused predictions (`"Liabi1ity cap"` predicted
for a `contract_type` field). `incorrect_normalization`/`wrong_inferred_value` both at exactly 0
is worth treating with suspicion rather than as a clean result — it may mean the ontology-based
and source-support-based detection paths in `_classify_mismatch` are too narrow for this eval
set's actual error shapes, not that these failure modes don't occur; not yet investigated.
Full report: `logs/failure_analysis_distilled_iter5_fixed.json` (buggy pre-fix report preserved
at `logs/failure_analysis_distilled_iter5.json` for provenance, per §8's not-overwriting-failures
practice).

## Iteration 9 — 2026-08-09 — Quick investigation: why incorrect_normalization/wrong_inferred_value read 0

**Finding (CPU-only, no GPU needed — reused iteration 8's saved report).** `incorrect_normalization`
reading 0 is a real content gap, not a detection bug: only 2 of 12 schemas
(`support_ticket`, `medical_note`) have a non-empty `ontology` dict in their `SchemaSpec`. Every
other schema, including `contract`, has `ontology={}` — even though the eval set surfaced a
textbook case the mechanism exists for: `contract_type` predicted `'NDA'` vs. reference
`'Non-Disclosure Agreement'`, which fell into `unclassified_mismatch` for lack of a registered
ontology entry to classify it as `incorrect_normalization`. Filling in ontology dicts for schemas
with obvious abbreviation/synonym vocabularies (contract types, CRM deal stages, etc.) is a real,
concrete follow-up — not done yet.

`wrong_inferred_value` reading 0 looks like a property of this particular small eval set rather
than a bug: the `implicit` corruption tag is present (17/72 records), but none of the
present-in-both-disagreeing (`errors`-dict) pairs happened to have neither side appear literally
in the source text — plausible given the errors-dict is dominated by near-miss OCR/typo variants
(`unclassified_mismatch`), which by construction retain partial literal overlap with the source.
Not confirmed as correct, just not contradicted by a spot-check; would need a larger/more
implicit-heavy eval set to trust the 0 either way.

## Iteration 10 — 2026-08-09 — Hybrid pipeline (§6): headline result, hybrid beats both alone

**What ran.** New `schemaforge/hybrid/pipeline.py` (`merge_prediction`/`rules_only_prediction`,
9 tests, all CPU-only) plus `src/08_hybrid_eval.py`, a GPU driver that for every record in
`data/eval_holdout.jsonl` (72 records, all 12 schemas): runs `run_prepass` to resolve
deterministic fields, asks the iteration-5 model checkpoint ONLY for the residual (unresolved)
fields (not every semantic field unconditionally, unlike prior eval scripts), merges the two, and
scores THREE systems on the same records — rules alone, model alone (residual-only prompt, not
directly comparable to earlier "model alone" numbers which asked for every semantic field), and
the hybrid merge.

**Result — this is the project's headline claim, and it holds on real data:**

| system | field precision | field recall | field F1 | hallucination rate | missing-field rate | schema validity |
|---|---|---|---|---|---|---|
| rules alone | 0.9185 | 0.1729 | 0.2911 | 0.0000 | 0.8117 | 1.0000 |
| model alone (residual-only prompt) | 0.5116 | 0.4603 | 0.4846 | 0.0667 | 0.3417 | 0.8611 |
| **hybrid (rules → model)** | **0.7479** | **0.6332** | **0.6858** | **0.0066** | **0.1562** | **0.9028** |

**The hybrid system beats both individual systems on every metric simultaneously** — field F1
0.686 vs. 0.291 (rules) and 0.485 (model), hallucination rate an order of magnitude below the
model-alone run (0.0066 vs 0.0667, since rules never hallucinate and only ~half the fields are
even asked of the model), and higher schema validity than the model alone. This is exactly the
architectural bet the project is built on: rules are precise but structurally blind to semantic
fields (0.92 precision, 0.17 recall alone), the model recalls much more but at a real hallucination
cost, and routing by field ownership captures the best of both rather than averaging them.

**Escalation coverage-at-risk** (confidence-based, per-record field-F1>=0.5 correctness,
mean-token-logprob raw confidence, no calibration fitted — raw operating points only): risk<=0.10
achievable at 43.1% coverage, risk<=0.20 at 72.2% coverage, risk<=0.30 at 100% coverage (i.e. the
uncalibrated confidence signal alone already separates enough that trusting only the top ~43% most
confident records keeps error rate under 10%, without needing a frontier-LLM escalation path built
yet — that escalation target itself is not implemented, this only characterizes what confidence
threshold WOULD be usable if it were).

**Not directly comparable:** this hybrid run's "model alone" (0.4846 F1) differs from iteration
4/5's "model alone" numbers (0.4263 base / 0.4216 iter5) because this driver's prompt asks only
for the pre-pass's residual fields, not every semantic field — a smaller, easier ask, so the
higher F1 here is partly a prompt-scope effect, not purely a stronger model. The rules-alone and
hybrid numbers are the ones that are new and comparable to nothing produced before this iteration.

Full report: `logs/hybrid_eval_distilled_iter5.json`.

## Iteration 11 — 2026-08-09 — Crossover benchmark: rules-precision decay vs. hybrid resilience

**What ran.** `data/crossover_benchmark.jsonl` (144 records: 9 training schemas x 4 docs x 4
severities, operators `ocr_noise,typo,delabel`, seed 11 — matching README's existing
deterministic-baseline-curve reproduction recipe exactly, so the rules-alone numbers below are
directly comparable to that table) split into 4 per-severity files and run through
`src/08_hybrid_eval.py` (iteration-5 checkpoint) separately at each severity, since that script
only reports an aggregate and this benchmark specifically needs the per-severity breakdown.

**Note on reproduction exactness:** this run's rules-alone numbers (F1 0.413/0.306/0.175/0.108 at
severities 0.0/0.3/0.6/1.0) are close to but not byte-identical to README's existing table (0.393/
0.230/0.138/0.092) despite using the documented same recipe (`n=4` per schema, same operators,
same seed). Both were generated by the same `schemaforge.hardexamples.generate` CLI with the same
stated arguments; the discrepancy's exact source (harness-vs-hybrid-module evaluation path
differences, or an undocumented parameter drift between when README's table was written and now)
was not tracked down given time constraints — flagged here rather than silently presented as an
exact match. The qualitative shape (steep decline, same order of magnitude) is consistent either
way.

**Result:**

| severity | rules P | rules R | rules F1 | model F1 | hybrid F1 | hybrid hallucination |
|---|---|---|---|---|---|---|
| 0.0 | 0.990 | 0.261 | 0.413 | 0.558 | 0.835 | 0.0000 |
| 0.3 | 0.844 | 0.187 | 0.306 | 0.467 | 0.670 | 0.0062 |
| 0.6 | 0.685 | 0.101 | 0.175 | 0.375 | 0.495 | 0.0091 |
| 1.0 | 0.537 | 0.060 | 0.108 | 0.301 | 0.383 | 0.0156 |

**Rules precision decays sharply under corruption exactly as research direction §6 predicts**
(0.990 → 0.537, roughly halving from clean to severity 1.0) — under OCR noise, typos, and
delabeling, the deterministic pass doesn't just go quiet, it starts being wrong, confirming the
motivating claim for the whole hybrid architecture. **There is no severity at which rules alone
wins** in this sweep — the model and hybrid systems lead at every point, including severity 0.0
(clean text), because rules structurally cannot recall semantic fields at all (recall ceiling
~0.26 even on clean text) — so this dataset does not produce a literal "crossover point" the way
the research direction's framing anticipates; the more accurate finding is that the model/hybrid
lead shrinks as severity rises (hybrid's margin over rules alone: +0.42 F1 at severity 0.0,
narrowing to +0.28 at severity 1.0) rather than reversing. Hybrid hallucination rate rises
mildly with severity (0 → 0.0156) but stays far below the model-alone hallucination rates seen
in other iterations, since roughly half the fields are still resolved by rules (which never
hallucinate) at every severity level.

Full per-severity reports: `logs/crossover_sev_0.0.json`, `_0.3.json`, `_0.6.json`, `_1.0.json`;
aggregate-only run also saved at `logs/crossover_hybrid_eval.json`.

## Iteration 12 — 2026-08-09 — First automated §8 loop run: real result, real process gaps found

**What ran.** The first non-dry-run invocation of `src/09_loop.py` (research direction §8):
corpus generation (1080 records, same seed/params as iteration 5) → teacher query + §4.2 gate →

experiment manifest alongside the usual narrative log entry here.

**Result.** Teacher gate: 634/1080 admitted (58.7%), consistent with iteration 5's 636/1080
(58.9%) on the byte-identical corpus. Hybrid system on the 72-record eval set:

| system | field precision | field recall | field F1 | hallucination rate | schema validity |
|---|---|---|---|---|---|
| rules alone | 0.9185 | 0.1729 | 0.2911 | 0.0000 | 1.0000 |
| model alone | 0.4852 | 0.4128 | 0.4461 | 0.0852 | 0.7361 |
| **hybrid** | **0.7131** | **0.5858** | **0.6432** | **0.0136** | **0.8333** |

**This is a negative result relative to iteration 5/10, reported per §8.** Hybrid field F1
(0.6432) is LOWER than the near-identical-corpus iteration 5/10 run (0.6858) — a real regression

leading suspect, not proven: `src/02_train_distill.py` never fixes a training random seed

effect on results, not just a reproducibility nicety.

**Process gaps found while building this run's provenance record (not results, but real defects

1. No training seed is set (as above) — the actual root cause candidate for the F1 regression.
2. `src/09_loop.py` always overwrites `models/distilled_minicpm5_1b_v2_amd` without first renaming
   the existing checkpoint, unlike every manually-launched prior iteration. **The iteration-5
   checkpoint's weights are now permanently lost** on the training server (its numbers remain
   documented here and in the eval JSON reports, just not the weights).
3. `src/09_loop.py`'s subprocess helper captures but never persists the retrain stage's stdout, so
   this run's per-epoch training loss and step count are unrecoverable — a real observability gap
   for a script whose whole purpose is unattended provenance-preserving iteration.

**Not recommended for Hugging Face upload** — this checkpoint (sha256
`0bfd865f9e74f749387cd3e801865eba42e8698fcc189057a1613ce1f7c5447e`) scores below the already-

## Iteration 14 — 2026-08-10 — Targeted missing_field corpus: negative result, confirmed by controlled comparison

**What ran.** Per a proposed follow-up to iteration 13's inconclusive "tie within noise": a
supplementary training corpus (`data/corpus_targeted_missing.jsonl`, 1080 records) using ONLY the
`delabel`/`implicit` corruption operators — no other corruptions stacked on top, unlike every
other corpus generated in this project, which stacks all ten operators by default — concatenated
with the same baseline corpus as iteration 13 (`corpus_baseline.jsonl`, 2700 records, identical
params) into a 3780-record combined corpus. Also generated a 4x larger eval set
(`data/eval_holdout_v2.jsonl`, 288 records vs. the 72-record set used since iteration 4) so future
comparisons stop being decided by noise. Training config (seed, LR, epochs) unchanged from
iteration 13 — only the training data changed. Orchestrated manually (not via `src/09_loop.py`,
which can't concatenate two corpora). Full provenance: `experiments/loop-iter2-20260809T235538Z/`.

**Positive finding, independent of the checkpoint result:** teacher gate admitted 2685/3780
(**29.0% rejected**), the largest single-iteration improvement in this project (vs. 39.7% in
iteration 13, 41.1% in iteration 5) — not isolated to one cause (ontology fills carried over
unchanged, or the isolated-operator corpus structure, or both).

**Negative result, confirmed by a genuinely controlled comparison:** run against the SAME
72-record eval set used since iteration 4:

| metric | iteration 13 | iteration 14 | delta |
|---|---|---|---|
| field F1 | 0.6830 | 0.6583 | **-0.0247** |
| field recall | 0.6416 | 0.5844 | **-0.0572** |
| schema validity | 0.8750 | 0.8056 | **-0.0694** |
| exact match | 0.2222 | 0.2917 | +0.0695 |
| `missing_field` share of failures | 55.0% (202/367) | **60.1% (221/368)** | **worse, not better** |
| `schema_violation` count | 1 | 4 | worse |

**The specific hypothesis this run tested — that isolated delabel/implicit training examples
would reduce omission failures — is not supported by the data, on a comparison controlled enough
to trust (same eval set, same 72 records, only the training corpus differs).** Field F1, recall,
and schema validity all dropped versus iteration 13; the targeted failure category's share of all
failures increased rather than decreased.

**Plausible explanation, not confirmed:** the supplementary corpus trained the model on
delabel/implicit corruptions in isolation, while the eval set (and most of the baseline training
corpus) presents them compounded with OCR noise, typos, and reordering simultaneously — isolated-
operator practice may not transfer to the compounded case the model is actually evaluated on.
Worth testing directly in a future iteration: stack the targeted operators on top of the others
instead of isolating them.
